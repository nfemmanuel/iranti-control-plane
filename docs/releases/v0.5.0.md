# Iranti Control Plane — v0.5.0 Release Notes

**Status:** Release Candidate — 2026-03-22 (pending GitHub Release tag)
**Previous release:** v0.4.0
**Phase:** 5 — Session Recovery & Runtime Lifecycle
**Iranti upstream requirement:** v0.2.16 or later

---

## What's in v0.5.0

v0.5.0 surfaces the capabilities that arrived in Iranti v0.2.16. That upstream release added durable session recovery, runtime lifecycle tracking, and upgrade coordination — but without this control plane release, none of it was visible to operators. Before v0.5.0, session state was invisible, instance processes were opaque, and upgrading Iranti required a terminal.

v0.5.0 closes all three gaps. It also submits the long-pending CP-T025 upstream PR (native Attendant and Resolutionist Staff event emission) and completes the clean-machine installer validation that was the sole remaining gate for v0.3.0 and v0.4.0 GitHub Releases.

This release ships 5 tickets across Waves 11–12 (Phase 5), all PM-ACCEPTED on 2026-03-22.

## New Features

### Session Recovery View

**CP-T071 — Wave 11**

A new `/sessions` route in the control plane gives operators full visibility into session state for the first time.

Before v0.5.0, if an agent session was interrupted mid-task, the only way to know was to query the Iranti database directly. Now:

- **Sessions list** with filter tabs: All / Interrupted / Active / Complete / Abandoned
- **State badges** with semantically correct colors: amber for interrupted/checkpointed sessions that need attention, emerald for complete, muted gray for abandoned, rose for unknown state
- **Per-session detail panel** (inline expand): full session ID (copyable), agent ID linked to Agent Registry, full task text, timeline from start through last checkpoint through terminal state, raw checkpoint JSON (collapsible)
- **Resume action**: for sessions in interrupted or checkpointed state, operators can resume the session directly from the control plane (calls `POST /memory/resume` on the Iranti instance)
- **Abandon action**: operators can formally mark an interrupted session as abandoned with confirmation (calls `POST /memory/abandon`)

The Sessions nav item is inserted between Agents and Health in the AppShell sidebar.

**What this means for you:** When an agent crashes mid-task, you no longer need to query the database to understand what was running. You can see all interrupted sessions, read the checkpoint state, and decide to abandon cleanly — from the control plane.

### Runtime Lifecycle Status in Instance Manager

**CP-T072 — Wave 11**

The Instance Manager now shows whether an Iranti instance's process is genuinely running, stale, or stopped — not just whether the port responds.

Before v0.5.0, the Instance Manager showed "Reachable" or "Unreachable." This conflated "port responds to HTTP" with "the process is healthy." An instance could show Reachable while the underlying process was hanging or had crashed without a clean shutdown.

Iranti v0.2.16 added a `runtime.json` heartbeat file and a `runtime` field in `GET /health`. v0.5.0 uses this data:

- **Runtime status badge** per instance card:
  - `RUNNING ●` (emerald) — process is live, heartbeat within 60 seconds
  - `STALE ⚠` (amber) — runtime.json says running but last heartbeat is older than 60 seconds; process may have crashed without clean shutdown
  - `STOPPED ○` (muted gray) — clean shutdown confirmed
  - No badge — instance not launched via `iranti run` (ad-hoc mode)

- **Process detail fields** on instance cards with runtime data: Iranti version, PID, started relative time, last heartbeat relative time
- **Stale warning callout**: when a process is stale, the card shows an amber callout with the exact `iranti run --instance <name>` restart command
- **Overview Dashboard update**: the System Status Strip now includes an amber dot when any instance has a stale runtime signal

**What this means for you:** If a process crashes overnight, you will see an amber `STALE ⚠` badge in the morning rather than a healthy-looking "Reachable" status.

### Upgrade Coordination from Instance Manager

**CP-T073 — Wave 12**

Operators can now trigger `iranti upgrade --restart --instance <name>` from the Instance Manager — no terminal required.

Before v0.5.0, upgrading a running Iranti instance required opening a terminal, running the upgrade command, watching for output, and coming back to the control plane to verify the version. This broke the "operate Iranti without a terminal" premise.

The upgrade flow:

1. In the Instance Manager, expand an instance's detail panel
2. An **Upgrade** section shows the currently running Iranti version
3. Click **Upgrade & Restart** — a confirmation modal explains the instance will restart and active agents will experience a brief interruption
4. After confirming, the control plane spawns the upgrade job asynchronously (returns a job ID immediately)
5. A live output panel polls the job every 2 seconds and streams process output in real time
6. On success: confirmation message; runtime status refreshes to show the new version
7. On failure: error message with the last N lines of output and a Try Again button

The backend validates the instance name (alphanumeric, hyphen, underscore only — no shell injection), checks that the `iranti` CLI is on PATH, and writes upgrade attempts to the audit log.

**What this means for you:** Staying current with Iranti no longer requires a terminal session. The entire upgrade + verify cycle happens inside the control plane.

## Upgrade Notes

**Iranti version requirement:** v0.5.0 requires Iranti v0.2.16 or later on the connected instance. The session recovery view, runtime lifecycle badges, and upgrade coordination all depend on APIs and data structures introduced in v0.2.16.

If you are running an earlier Iranti version:
- The Sessions view will render but show an empty state (no session data)
- Instance cards will show no runtime badge (runtime field is null in pre-v0.2.16 health responses)
- The upgrade action requires the `--restart --instance` flags added in v0.2.16

**No breaking changes:** All v0.4.0 surfaces (Overview Dashboard, Health Dashboard, Memory Explorer, Staff Logs, etc.) continue to work without modification.
