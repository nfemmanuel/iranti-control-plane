# Iranti Control Plane — v0.7.0 Release Notes

**Status:** Released — 2026-03-22
**Previous release:** v0.6.0
**Phase:** 7 — Operator Configuration Management
**Iranti upstream requirement:** v0.2.16 or later

---

## What's in v0.7.0

v0.7.0 closes the configuration management gap. Before this release, the control plane could show you the state of your Iranti instance — providers, keys, instances, project bindings, integrations — but could not change any of it. Everything writable required the terminal: `iranti add api-key`, `iranti configure instance`, `iranti project init`, `iranti claude-setup`.

v0.7.0 makes all of these writable from the control plane. Operators can now rotate provider API keys, configure fallback chains, set per-task model routing, create and configure instances, bind and rebind projects, scaffold Claude Code and Codex integrations, manage Iranti client API keys, and debug the Attendant's memory retrieval logic — all without opening a terminal.

This release ships 11 tickets across Waves 17–21 (Phase 7), all PM-ACCEPTED on 2026-03-22. (CP-T094 was closed as already delivered in CP-T071.)

## New Features

### Provider Key Write Path

**CP-T085 — Wave 17**

The Provider Manager is no longer read-only. Operators can now add, update, and remove upstream provider API keys directly from the UI.

- **"Manage Key"** action per configured provider (OpenAI, Claude, Gemini, Groq, Mistral)
- **"Add Key"** action for providers not yet configured
- Inline form with masked current key (last 4 chars), write-only update field, and "Remove Key" with confirmation
- Placeholder detection: values like `sk-xxx`, `replace_me`, or `your_api_key` are rejected at the backend before any write
- Writes target the live instance env file (`IRANTI_INSTANCE_ENV` pointer) using the same variable names as the Iranti CLI: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `GROQ_API_KEY`, `MISTRAL_API_KEY`
- Raw key values are never returned in API responses — write-only semantics enforced end to end
- Provider reachability status refreshes automatically after a key update

**Backend routes:** `PUT /api/control-plane/providers/:provider/key`, `DELETE /api/control-plane/providers/:provider/key`

**What this means for you:** Key rotation no longer requires a terminal. Open the Provider Manager, click Manage Key, paste the new key, save.

### Provider Default + Fallback Chain Configuration

**CP-T086 — Wave 17**

Operators can now set the default LLM provider and configure the high-availability fallback chain from the Provider Manager.

- **Default provider selector**: dropdown with all known providers (gemini, claude, openai, groq, mistral, ollama, mock). Changing it writes `LLM_PROVIDER` to the instance env and triggers a reachability refresh.
- **Fallback chain editor**: shows the current `LLM_PROVIDER_FALLBACK` as an ordered list (e.g. "openai → groq → mock"). "Edit Fallback Chain" opens an inline editor with add/remove and up/down reorder controls.
- On save, the backend writes `LLM_PROVIDER_FALLBACK` as a comma-separated string to the instance env.
- "No fallback configured" is shown as an informational state, not an error.
- "Clear fallback chain" removes `LLM_PROVIDER_FALLBACK` entirely.

**Backend routes:** `PUT /api/control-plane/providers/default`, `PUT /api/control-plane/providers/fallback`, `DELETE /api/control-plane/providers/fallback`

**What this means for you:** If OpenAI goes down, you can configure a groq → mistral → mock fallback from the control plane in under a minute. No env file editing required.

### Provider Task-Model Routing Editor

**CP-T087 — Wave 17**

Operators can now configure per-task model routing from the Provider Manager — the primary cost-optimization lever for Iranti deployments.

Iranti supports six task-specific model overrides:

| Task type | Env var |
|-----------|---------|
| Classification | `CLASSIFICATION_MODEL` |
| Relevance | `RELEVANCE_MODEL` |
| Summarization | `SUMMARIZATION_MODEL` |
| Task inference | `TASK_INFERENCE_MODEL` |
| Extraction | `EXTRACTION_MODEL` |
| Conflict resolution | `CONFLICT_MODEL` |

The Task Routing section in the Provider Manager shows the current model for each task type (or "Using default" if not overridden) with a per-task Override dropdown populated with models known for the active provider. Incompatible selections (e.g. a Gemini model when `LLM_PROVIDER=openai`) are flagged inline.

"Reset All Overrides" clears all six task-model env vars in one action.

**Backend route:** `PUT /api/control-plane/providers/task-routing`

**Known drift:** A pre-existing inconsistency was surfaced during this ticket: the control plane writes `LLM_PROVIDER=anthropic` while the Iranti router expects `claude`. This is tracked as CP-T097 (bug, filed separately).

**What this means for you:** Set `CLASSIFICATION_MODEL=gemini-2.5-flash` and `CONFLICT_MODEL=gemini-2.5-pro` from the control plane. No env file editing required.

### Iranti Client API Key Manager

**CP-T088 — Wave 18**

The Instance Manager now has a full API key management surface for the Iranti registry-backed keys used by agents, Claude Code integrations, and project bindings.

These are distinct from upstream provider keys (covered by CP-T085). These are the tokens that authenticate agent HTTP calls against your Iranti instance (`X-Iranti-Key` header).

- **Key list**: all registered keys per instance with key ID, owner label, scopes (displayed as readable tags: `kb:read`, `memory:write`, etc.), creation and last-modified timestamps, and active/revoked status
- **Create Key** form: key ID, owner label, scope selector (checkboxes for standard scopes plus free-text for namespace-aware scopes like `kb:read:project/acme`), and "Copy to project" (syncs the token into a bound project's `.env.iranti`)
- After creation, the generated token is shown exactly once in a copy-only field with a clear "will not be shown again" warning
- **Revoke Key** marks the key inactive with a confirmation dialog; revoked keys remain visible in the list for audit purposes
- Token generation uses the same cryptographic approach as the Iranti CLI (`keyId.secret` format; only the hashed form is stored in the DB)
- The backend never returns raw token values — write-once display on creation only

**Backend routes:** `GET /api/control-plane/auth-keys`, `POST /api/control-plane/auth-keys`, `DELETE /api/control-plane/auth-keys/:keyId`

**What this means for you:** When a project needs a new API key, or a key is compromised and needs revocation, you no longer need standalone scripts or the CLI. The entire key lifecycle — create, scope, sync, revoke — lives in the control plane.

### Instance Create

**CP-T089 — Wave 19**

The Instance Manager can now create new Iranti instances without using the terminal.

A **"Create Instance"** button in the Instance Manager header opens a four-step form:

1. **Name + port** — alphanumeric/underscore name, port (defaults to next available after 3001), port conflict detection
2. **Database URL** — full PostgreSQL connection string with format hints and placeholder rejection
3. **Provider** — dropdown plus API key field (if a remote provider is selected)
4. **Review + Create** — summary before write

After creation, the new instance appears in the list in "stopped" state with a Start button immediately available. The backend writes the instance directory structure using the same layout as the Iranti CLI.

**Backend route:** `POST /api/control-plane/instances`

**Note:** If the instance database requires migrations, the response includes a `dbMigrationNote` field indicating that `iranti db migrate --instance <name>` should be run before the instance is started for the first time.

**What this means for you:** Spinning up a second Iranti instance for a staging environment or team project no longer requires a terminal session.

### Instance Configure

**CP-T090 — Wave 19**

Existing instances can now be reconfigured from the Instance Manager.

A **gear icon** on each instance card opens an instance configuration panel showing the current values for:
- Port (`IRANTI_PORT`)
- Database URL (`DATABASE_URL`) — displayed masked (scheme://user:****@host:port/db)
- Provider (`LLM_PROVIDER`)

All three fields are editable. On save, the backend writes the updated values to the instance env file using the same merge strategy as `iranti configure instance` (read existing, update target vars, write back — no unrelated vars are lost). If the instance is currently running, the panel shows a restart-required warning with a "Restart Now" button.

**Backend route:** `PATCH /api/control-plane/instances/:name`

**What this means for you:** When PostgreSQL is migrated or a port conflict appears after a system change, you can reconfigure the instance from the control plane. No hand-editing of env files.

### Project Binding Create + Rebind

**CP-T091 — Wave 19**

The Instance Manager now supports creating new project bindings and rebinding existing ones to different instances.

**Bind Project:**
- Each instance has a "Bind Project" button that opens a form: project directory path, mode (isolated / shared), agent ID, and memory entity
- On submit, the backend writes `.env.iranti` into the project directory with `IRANTI_URL`, `IRANTI_API_KEY`, `IRANTI_AGENT_ID`, `IRANTI_MEMORY_ENTITY`, `IRANTI_PROJECT_MODE`, `IRANTI_INSTANCE`, and `IRANTI_INSTANCE_ENV`
- The project path is validated to exist and be a directory before any write
- `.env.iranti` is added to the project's `.gitignore` (same as CLI behavior)
- The new binding appears in the instance's project list immediately

**Rebind:**
- Each existing project binding has a "Rebind" action with a new instance selector
- On submit, `IRANTI_URL`, `IRANTI_API_KEY`, `IRANTI_INSTANCE`, and `IRANTI_INSTANCE_ENV` are updated while `IRANTI_AGENT_ID`, `IRANTI_MEMORY_ENTITY`, and `IRANTI_PROJECT_MODE` are preserved
- The binding moves to the new instance in the UI after rebind

**Backend routes:** `POST /api/control-plane/instances/:name/projects`, `PATCH /api/control-plane/instances/:name/projects/:projectId`

The binding registry is maintained as `projects.json` in the control plane data directory, updated atomically on every bind/rebind operation.

### Claude Code Integration Manager

**CP-T092 — Wave 20**

Operators can now inspect, diagnose, and scaffold Claude Code integration files for each bound project from the control plane.

**Visibility:**
- Per-project "Claude Integration" expandable section showing `.mcp.json` and `.claude/settings.local.json` status, content summaries (MCP servers registered, hooks configured), and whether `IRANTI_URL` in `.env.iranti` matches what the integration files expect
- Six diagnostic issues are detected and shown with specific failure-mode explanations:
  - `.mcp.json` not found
  - Iranti MCP server not registered in `.mcp.json`
  - `iranti` command not found on PATH
  - Hook command uses an absolute path that may break after reinstall
  - `IRANTI_URL` mismatch between `.env.iranti` and `.mcp.json`
  - Settings file invalid JSON
- Read-only code viewer for `.mcp.json` and `settings.local.json` content

**Scaffolding:**
- **"Scaffold Claude Integration"** button writes or updates `.mcp.json` and `.claude/settings.local.json` via direct file write (maintaining parity with `iranti claude-setup` output)
- If files already exist, a confirmation shows: "Existing MCP servers other than Iranti will be preserved"
- **"Re-scaffold (force)"** option for overwriting stale files with a fresh generation
- Integration summary refreshes after scaffolding

**Backend routes:** `GET /api/control-plane/instances/:name/projects/:projectId/claude-integration`, `POST /api/control-plane/instances/:name/projects/:projectId/claude-integration/scaffold`

### MCP and Hook Visibility

**CP-T093 — Wave 20**

A new Integrations section in the Instance Manager provides an aggregated view of MCP server registrations and Claude Code hook configurations across all bound projects.

- Per-project integration summary: MCP server count, whether `iranti` is registered, hook event count, file health status
- Expandable per-project detail: full MCP server list (name, command, args), full hook list (event, matcher, command)
- Known issues highlighted inline (missing Iranti MCP, stale binary path, invalid JSON) with "Quick Fix → Scaffold" actions
- The nine Iranti MCP tools are listed for each project where Iranti MCP is registered (`iranti_handshake`, `iranti_attend`, `iranti_observe`, `iranti_query`, `iranti_search`, `iranti_write`, `iranti_ingest`, `iranti_relate`, `iranti_who_knows`) with availability status based on current connectivity

**Backend route:** `GET /api/control-plane/integrations`

### Codex Integration Manager

**CP-T095 — Wave 21**

Operators using Codex can now see and manage the Codex integration state from the control plane.

- **Detection:** whether Codex is installed on the machine running the control plane server (platform-correct `which`/`where` check)
- **Registration status:** whether Iranti is registered with Codex and what project path is registered
- **"Register with Codex"** action runs `iranti codex-setup` as a subprocess and refreshes state
- **"Remove Codex Registration"** removes the registration with confirmation
- Error state when Codex is not found: clear "not installed" message

This is a machine-level integration (Codex global config), not per-project — it appears as a top-level section in the Integrations view.

**Backend routes:** `GET /api/control-plane/integrations/codex`, `POST /api/control-plane/integrations/codex`, `DELETE /api/control-plane/integrations/codex`

### Attendant Debug Tools

**CP-T096 — Wave 21**

A new Attendant Debug panel in the Health dashboard gives operators a way to inspect what the Attendant would surface for a given agent and task — without using the terminal.

**Manual Handshake:**
- Inputs: agent ID, task description
- Output: the working memory brief the Attendant would generate — working memory items (entity, key, summary, confidence), session recovery state, inferred task type
- Displayed as structured cards with a "View raw JSON" toggle

**Manual Attend:**
- Inputs: agent ID, query text, optional context
- Output: memory blocks retrieved for the query with entity, key, and confidence scores

Both tools proxy through the control plane backend to the live Iranti instance using `X-Iranti-Key` auth. The `currentContext` field is correctly mapped (not `context` — a prior spec drift that was corrected in this implementation).

**RC fix applied:** During live smoke validation against Iranti v0.2.21, the handshake and attend proxy bodies were found to send `agentId` where the Iranti memory API expects `agent`. The proxy bodies were corrected before release (`attendant-debug.ts:141,189`). The UI-facing field name (`agentId`) is unchanged.

**Backend routes:** `POST /api/control-plane/debug/handshake`, `POST /api/control-plane/debug/attend`

**What this means for you:** When memory isn't loading correctly for an agent, you can run a manual handshake from the control plane and see exactly what the Attendant would return — before filing a bug or diving into logs.

## Upgrade Notes

**No breaking changes to v0.6.0 surfaces.** All existing routes, views, and env resolution behavior are preserved.

**Env write semantics:** All write operations in v0.7.0 use a merge strategy: read existing env file, update target variable(s), write back. Unrelated variables are never removed. This matches the behavior of `iranti add api-key`, `iranti configure instance`, and `iranti project init`.

**Iranti restart after env writes:** The Iranti process loads its runtime env once at startup via `loadRuntimeEnv()`. Any provider key, default provider, or fallback chain change requires a restart before taking effect. The control plane shows a restart warning after every env write and offers a "Restart Now" button where applicable.

**Instance env path resolution:** All writes target the instance env file located via `IRANTI_INSTANCE_ENV` in the project binding pointer (`.env.iranti`). The path resolution chain is: binding pointer → `IRANTI_INSTANCE_ENV` → live instance env. No writes go to the project-level `.env.iranti` binding file except for project bind/rebind operations.

**Known drift — anthropic/claude provider ID:** The control plane writes `LLM_PROVIDER=anthropic` when "Claude" is selected as the default provider. The Iranti LLM router expects `claude`. This is a pre-existing inconsistency in the upstream Iranti environment variable contract. It is tracked as **CP-T097** and will be resolved in the next release. Workaround: set `LLM_PROVIDER=claude` manually in the instance env if using Claude as the default provider.

## Known Gaps

| Gap | Severity | Notes |
|-----|----------|-------|
| anthropic/claude provider ID drift (CP-T097) | Medium | Control plane writes `LLM_PROVIDER=anthropic`; Iranti router expects `claude`. Pre-existing inconsistency. Tracked in CP-T097. |
| DB migration prompt is informational only | Low | Instance Create notes when migrations may be needed but does not run `iranti db migrate` automatically. Operator must run it manually before first start. |
| Project directory picker | Low | Project Binding Create uses a text input for the path (not a native directory picker). Browser `webkitdirectory` is available on supported browsers but was deferred. |
| Codex unregister CLI command | Low | Codex deregistration delegates to `iranti uninstall --target codex`; if this CLI subcommand is not available in the installed version, a manual fallback instruction is shown. |
| PID tracking cleared on control plane restart | Low | Carried forward from v0.6.0. In-memory PID map is lost on server restart. Use Start to reconnect tracking. |
