# Iranti Control Plane — v0.6.0 Release Notes

**Status:** Release Candidate — 2026-03-22 (pending GitHub Release tag)
**Previous release:** v0.5.0
**Phase:** 6 — Actionable Control Plane
**Iranti upstream requirement:** v0.2.16 or later

---

## What's in v0.6.0

v0.6.0 is the "actionable control plane" release. It makes two significant shifts simultaneously.

The first is functional: before v0.6.0, the control plane could report problems but not fix them. You could see that Iranti was unreachable, but you had to open a terminal to start it. You could see that your installation was outdated, but you had to run an npm command to update it. A new user who opened the control plane before installing Iranti saw a wall of red health checks with no guidance. v0.6.0 turns all of this around — the control plane can now start and stop Iranti instances, trigger upgrades, detect whether Iranti is installed at all, and guide new operators through first-time setup step by step.

The second is visual: before v0.6.0, the control plane used the "Terminals" dark blue-gray + emerald palette chosen in Phase 0. The iranti-site marketing product had moved to a warm amber + teal + warm-ink palette, meaning both products looked like they belonged to different companies. v0.6.0 migrates the control plane's design system to match the iranti-site palette exactly — warm near-black backgrounds, amber interactive elements, teal health indicators, Inter typography.

This release ships 8 tickets across Waves 13–16 (Phase 6), all PM-ACCEPTED on 2026-03-22.

## New Features

### Brand Palette Migration — Amber + Teal + Warm Ink

**CP-T076 — Wave 13**

The entire design system has been rebuilt around the iranti-site palette.

**Dark mode:** Page background is warm near-black (`#080808`). Card surfaces are `#111110`. Interactive elements (buttons, active nav items, links) render in amber (`#f59e0b`). Health indicators use teal (`#14b8a6`) — a distinct hue from the amber CTA family, ensuring healthy status never looks like an action prompt. Warning badges use amber-orange (`#f97316`). Error states use red (`#ef4444`). Typography uses Inter as the primary sans-serif, loaded from Google Fonts with a full system stack fallback.

**Light mode:** Background is warm sand off-white (`#faf9f7`). Text is warm near-black (`#1c1c1a`). The amber and teal accents shift to darker, higher-contrast variants for WCAG AA legibility against light backgrounds.

**Staff component identity colors** are preserved: Librarian amber, Attendant violet, Archivist sky, Resolutionist teal. Resolutionist teal now aligns with the success/health teal — this is intentional, as conflict resolution is semantically a success-class action.

All color values flow through `tokens.css` design tokens. No hardcoded hex values remain in component CSS.

**What this means for you:** The control plane and the iranti-site now look like a coherent product family.

### Version Sync: Up-to-Date Status in Health Dashboard

**CP-T078 — Wave 14**

The Health Dashboard now shows whether your Iranti installation is current.

A new version status row appears at the top of the Health Dashboard:

- **Up to date:** `Iranti v0.2.16  ✓ Up to date` (teal)
- **Update available:** `Iranti v0.2.16  ↑ Update available: v0.2.17  [Release notes ↗]` (amber-orange)
- **Registry unavailable:** `Iranti v0.2.16  (unable to check for updates)` (neutral)
- **Instance unreachable:** `Iranti version unknown  (connect to an instance to check)` (neutral)

The backend fetches the installed version from the running Iranti instance's `/health` response and the latest published version from the npm registry (5-second timeout, 60-second server-side cache). Neither source failing causes a 500 — the endpoint always returns 200 with graceful null fields.

The "Release notes" link when an update is available points to the Iranti GitHub releases page.

**What this means for you:** You no longer need to run `npm show iranti version` in a terminal to know if an update exists.

### Iranti Install Detection

**CP-T079 — Wave 15**

The control plane now detects whether the `iranti` CLI is installed on the machine running the server.

A new "Iranti CLI" status section appears at the top of the Instance Manager:

- **Installed:** `✓ Installed — v0.2.16 · /usr/local/bin/iranti`
- **Not installed:** `✗ Not found · npm install -g iranti  [Copy]`

The Copy button copies the install command to the clipboard and shows a brief "Copied!" confirmation. When Iranti is not installed, the Instance Manager's empty state changes to guide the operator toward installation rather than showing cryptic connectivity errors.

Detection uses the platform-correct command (`which` on Unix, `where` on Windows) with a 3-second subprocess timeout.

### Process Lifecycle Controls — Start and Stop Instances

**CP-T080 — Wave 15**

The Instance Manager now has Start and Stop buttons for each instance.

- **Start** (shown for unreachable instances): calls `POST .../instances/:name/start`, spawns `iranti run --instance <name>` as a detached subprocess (unref'd — the instance continues running if the control plane restarts), then re-polls health after 2 seconds. If the process comes online, the card transitions to the running state automatically.
- **Stop** (shown for reachable instances): shows a confirmation modal warning that active agents will lose connectivity, then sends SIGTERM to the tracked process PID. On Windows, `process.kill()` is used.

Instance names are sanitized (alphanumeric, hyphen, underscore only) before being passed to the subprocess. Shell injection is not possible — `spawn` is used with an argument array, not `exec` with a shell string.

**Known limitation (documented in UI):** PID tracking is session-based. If the control plane server itself restarts, it loses track of previously spawned instances. The Start button can reconnect to a running instance after a control plane restart — only Stop is affected.

**What this means for you:** You can start and stop Iranti instances without opening a terminal.

### Promoted Upgrade Button

**CP-T081 — Wave 15**

When version sync (CP-T078) shows an update is available, an **Upgrade Iranti to vX.Y.Z** button appears prominently in the Instance Manager header — not buried in the instance detail panel.

The button uses the amber-orange warning color to signal that this is an impactful action. Clicking it shows a confirmation modal listing the instances that will be restarted, then triggers the CP-T073 upgrade job with live output streaming and success/failure states. After a successful upgrade, the version sync is re-fetched — the button disappears when the instance is current.

### Contextual Repair Actions on Health Check Cards

**CP-T082 — Wave 16**

Each failing health check in the Health Dashboard now shows a specific, actionable button rather than just a red indicator.

| Check | Failing Action |
|-------|---------------|
| `iranti_connectivity` | **Start Iranti** — triggers the CP-T080 start action and re-polls health |
| `iranti_auth` | **Configure API Key** — navigates to the Provider Manager |
| `db_connectivity` | **Check DB config** — expands an inline panel showing DB host/port/name (credentials masked); "Show full connection string" toggle reveals unmasked value |
| `vector_backend` | **View setup guide** — links to the Getting Started guide vector section |
| `ingest_roundtrip` | **Run diagnostics** — opens or focuses the CP-T059 Diagnostics Panel |
| `attend_check` | **View Attendant logs** — navigates to `/logs?component=attendant` |
| `vector_search_check` | **Check vector backend** — links to setup guide |

No action is shown when a check is passing. The repair buttons are additive to the existing CP-T033 general repair panel.

**What this means for you:** When something is wrong, the control plane tells you exactly what to do — not just that something is wrong.

### Guided Setup Wizard

**CP-T083 — Wave 16**

The control plane now takes over the full screen with a guided setup wizard when it detects that Iranti is not ready.

The wizard appears when either: (a) Iranti is not installed on the machine, or (b) no instance is configured and no instance is reachable. Once both conditions are met, the wizard dismisses and the normal shell appears.

**Four steps — each auto-detected:**

1. **Install Iranti** — shows the `npm install -g iranti` command with a copy button; auto-polls every 5 seconds until the CLI is detected; advances automatically
2. **Create an Instance** — name and port form; calls `iranti instance create` via the backend; advances when the instance directory is written
3. **Start Iranti** — Start button using the CP-T080 lifecycle endpoint; polls health every 2 seconds; advances when `iranti_connectivity` passes
4. **Configure API Key** — links to the Provider Manager for key entry; polls health every 5 seconds; shows "Finish" when `iranti_auth` passes

Steps already complete on app load are skipped automatically. If all conditions are already met, the wizard never appears. A "Skip setup" dismissal link is always visible — dismissal is remembered in localStorage (except for the "not installed" condition, which is non-dismissible since the product fundamentally cannot function without Iranti).

**What this means for you:** A new user who opens the control plane before installing Iranti sees a calm, guided, one-step-at-a-time setup experience instead of a dashboard full of red health checks.

## Upgrade Notes

**No breaking changes to existing surfaces.** All v0.5.0 views and endpoints continue to work.

**Design system change:** The palette migration (CP-T076) removes the old Terminals blue-gray/emerald palette entirely. Any custom CSS that referenced the old token names will need updating. No component CSS shipped with this product uses hardcoded hex values — all references go through tokens.

**PID tracking limitation:** The Start action introduced in CP-T080 tracks spawned process PIDs in memory. Restarting the control plane server clears the PID map. Instances spawned before the restart can still be started again via the UI (to reconnect tracking); Stop is the only action that requires the PID to be in-memory.

**Wizard localStorage:** The wizard dismissal state is stored in `localStorage` under the keys `iranti_setup_complete` and `iranti_setup_dismissed`. Clearing browser localStorage will cause the wizard to reappear on the next load if trigger conditions are met.

## Known Gaps

| Gap | Severity | Notes |
|-----|----------|-------|
| `iranti init` / `iranti instance create` CLI subcommand availability | Medium | Wizard Step 2 calls `POST .../instances/create` which delegates to the CLI. If the CLI command syntax differs from the spec, the backend will show a `manualCommand` fallback with a copy button. |
| In-memory PID tracking cleared on server restart | Low | Documented in the Instance Manager UI. Use Start to reconnect tracking after a control plane restart. |
