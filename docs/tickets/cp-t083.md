# CP-T083 — Guided Setup Wizard

**Type:** Feature (Frontend + Backend)
**Priority:** P1
**Assigned:** frontend_developer (primary) + backend_developer (polling endpoints)
**Phase:** 6 (Wave 16)
**Status:** OPEN
**Epic:** CP-E020 (Repair Actions) / CP-E010 (Installation & Onboarding)
**Depends on:** CP-T079 (install detection), CP-T080 (process lifecycle controls)

---

## Description

The control plane currently assumes the operator has Iranti installed, an instance configured, and the process running. For a brand-new user, none of these are true. The existing Getting Started screen (CP-T035, Phase 2) helps, but it does not guide the user step-by-step — it shows a checklist, not a wizard.

Phase 6 adds a **Guided Setup Wizard** that takes over the full screen when the control plane detects it is in a not-ready state. The wizard replaces the normal shell until all steps are complete. This is the onboarding moment — the operator's first impression of the product.

The wizard covers four steps:
1. Install Iranti
2. Create an instance
3. Start Iranti
4. Configure an API key

Once all four steps pass, the wizard is dismissed and the operator enters the normal control plane shell. The wizard can also be manually dismissed if the user already has a running instance (graceful escape hatch).

The design goal is an experience closer to Tailscale's first-run setup or Homebrew's installation prompt: clear, guided, with copy buttons and auto-detection. Not a wall of text — one step at a time.

---

## Trigger Conditions

The wizard is shown when **either** of these conditions is true on app load:

1. **Iranti is not installed** — `GET /api/control-plane/install-state` returns `installed: false`
2. **No instance configured AND no instance is reachable** — the Instance Manager has zero configured instances, OR all configured instances are unreachable

If Iranti is installed AND at least one instance is reachable (healthy or degraded): wizard is not shown. The normal shell renders.

**Important:** The wizard is also dismissible manually. Operators who have a running instance but see the wizard (edge case: slow health check on first load) can dismiss it without completing the steps.

## Wizard Steps

### Step 1 — Install Iranti

**Shown when:** `install-state.installed === false`

**Content:**
```
Install Iranti

Iranti is a local-first multi-agent memory layer.
Install it with npm:

  npm install -g iranti   [Copy]

Then press the button below to check detection.
```

**Copy button:** Copies `npm install -g iranti` to clipboard.

**Completion detection:**
- A "Check again" button triggers a re-fetch of `GET /api/control-plane/install-state`
- Alternatively: auto-poll every 5 seconds (so the step advances automatically once the operator finishes installing in their terminal)
- When `installed: true` is detected: step shows a green "Iranti detected — v0.2.16" confirmation for 1.5 seconds, then advances to Step 2

**Step is skipped if:** `install-state.installed === true` on first load. Wizard opens directly on Step 2.

---

### Step 2 — Create an Instance

**Shown when:** No instances are configured

**Content:**
```
Create your first Iranti instance

Give your instance a name:
  [ instance-name    ] (text input, placeholder "my-instance")

Port:
  [ 3001             ] (number input, default 3001)

  [Create Instance]
```

**What "Create Instance" does:**

Calls a new backend endpoint: `POST /api/control-plane/instances/create` (or a wizard-specific variant) which runs `iranti init --instance <name>` as a subprocess. This is similar to the Start subprocess in CP-T080 but uses `iranti init`.

Alternatively: if `iranti init` is not the correct command, the wizard shows the manual command to run in a terminal and polls for the new instance to appear. This is the fallback if `iranti init` does not exist as a CLI subcommand — check the current Iranti CLI surface before implementing.

**Validation:**
- Instance name: alphanumeric, hyphens, underscores; 1–64 chars; required
- Port: 1024–65535; required; default 3001

**Completion detection:**
- After `iranti init` completes (process exits 0): step shows a green confirmation and advances to Step 3
- If `iranti init` fails: show the error output inline with a "Try again" option

**Step is skipped if:** At least one instance is already configured. Wizard opens on Step 3.

---

### Step 3 — Start Iranti

**Shown when:** The configured instance is not currently reachable

**Content:**
```
Start your Iranti instance

Instance: my-instance (port 3001)

  [Start Iranti]
```

**What "Start Iranti" does:**

Calls `POST /api/control-plane/instances/:name/start` (CP-T080). Same flow as the Instance Manager Start button.

**Completion detection:**
- After calling Start: poll `GET /api/control-plane/health` (or instance health) every 2 seconds
- When `iranti_connectivity` check returns `passing`: step shows a green "Iranti is running" confirmation for 1.5 seconds, then advances to Step 4
- Timeout: if not healthy after 30 seconds, show "Still starting — this can take a few seconds. If it doesn't connect, check the terminal for errors."

**Step is skipped if:** The instance is already reachable. Wizard opens on Step 4.

---

### Step 4 — Configure API Key

**Shown when:** Iranti is running but `iranti_auth` health check is failing (no API key configured)

**Content:**
```
Configure your API key

Iranti connects to AI providers using API keys.
Add your Anthropic or OpenAI API key in the Provider Manager.

  [Open Provider Manager →]
```

**What "Open Provider Manager" does:**

Navigates to `/providers`. The wizard remains visually accessible (e.g., as a slide-out or a banner) so the operator can return to it after adding a key.

Alternatively: if the Provider Manager can be shown inline inside the wizard panel, embed a simplified version. This is a stretch goal — the primary deliverable is the navigation link.

**Completion detection:**
- Poll `GET /api/control-plane/health` every 5 seconds
- When `iranti_auth` check returns `passing`: show a green "API key configured" confirmation
- "Finish" button appears — clicking it dismisses the wizard and enters the normal shell

**Step is skipped if:** `iranti_auth` is already passing on wizard start.

---

## After Wizard Completion

When all applicable steps are complete (or skipped because the condition was already met):
- Show a brief "You're all set!" confirmation screen for 2 seconds
- Dismiss the wizard and render the normal AppShell with the Overview Dashboard (`/overview`)
- Write a flag to localStorage: `iranti_setup_complete: true` so the wizard does not reappear on subsequent sessions unless the trigger conditions return

---

## Dismissal Behaviour

The wizard has a **Dismiss** (or "Skip setup") link in the top-right corner, always visible.

Clicking Dismiss:
- Shows a brief confirmation: "Dismiss setup wizard? You can reopen it from the Help menu." — Confirm / Cancel
- On confirm: hides the wizard, enters the normal shell
- Sets a localStorage flag: `iranti_setup_dismissed: true`

If dismissed: the wizard does not reappear on reload unless `install-state.installed === false` (i.e., Iranti is literally not installed — that is the one condition where the wizard cannot be permanently dismissed, because the product fundamentally cannot function without Iranti).

## Backend Requirements

**New endpoint (if `iranti init` is the correct CLI command):**

```
POST /api/control-plane/instances/create
```

Body:
```typescript
interface CreateInstanceRequest {
  name: string;   // validated: alphanumeric + hyphen + underscore, 1–64 chars
  port: number;   // 1024–65535
}
```

Response:
```typescript
interface CreateInstanceResponse {
  name: string;
  port: number;
  status: 'created';
  createdAt: string;
}
```

Implementation: runs `iranti init --instance <name> --port <port>` (verify exact CLI flags against Iranti docs). Returns 202 if async, or 200 if synchronous. Returns 400 if name is invalid or port is out of range.

**If `iranti init` does not exist as a CLI command:** The endpoint returns a `manualCommand` string that the wizard displays to the user with a copy button.

## Acceptance Criteria

### AC-1 — Wizard shown when iranti not detected

On app load: if `install-state.installed === false`, the wizard is shown full-screen instead of the normal shell. The normal shell is not rendered behind it.

### AC-2 — Each step correctly detects completion before advancing

- Step 1: advances when `install-state.installed === true` (polled every 5s)
- Step 2: advances when `iranti init` process exits 0 (or when operator confirms manual setup)
- Step 3: advances when `iranti_connectivity` health check passes (polled every 2s)
- Step 4: advances when `iranti_auth` health check passes (polled every 5s)

No step auto-advances without confirmed detection. Steps do not advance on a timer alone.

### AC-3 — Wizard is dismissible

A "Skip setup" / "Dismiss" link is always visible. Clicking it shows a brief confirmation and then dismisses the wizard and enters the normal shell. The dismissal is remembered via localStorage so the wizard does not reappear on reload (except for the not-installed condition).

### AC-4 — Steps are skipped when conditions already met

If Iranti is installed on first load: Step 1 is skipped. If an instance is configured: Step 2 is skipped. If the instance is already reachable: Step 3 is skipped. If auth is passing: Step 4 is skipped. If all steps are skipped: wizard does not appear at all.

### AC-5 — Copy buttons work

All `npm install -g iranti` and command strings in the wizard have functional copy buttons. Copy buttons show a brief "Copied!" confirmation.

### AC-6 — Wizard does not appear on subsequent sessions when setup is complete

After the wizard completes (all steps pass), a localStorage flag prevents the wizard from appearing on the next app load unless a trigger condition (not installed, no reachable instance) returns.

### AC-7 — tsc clean

`tsc --noEmit` passes with 0 errors in both `src/server` and `src/client`.

## Priority

P1 — first-run experience. A new user who opens the control plane before installing Iranti currently sees a broken, cryptic dashboard with all health checks red. The wizard transforms that experience into a guided, actionable flow.

## Design Notes

- The wizard should feel calm and trustworthy, not alarming. Even though all health checks are failing, the wizard communicates "here is what to do next" — not "something is wrong."
- Progress through steps should feel rewarding — use the success teal (`--color-success`) for completion states. Each passing step should feel like a small win.
- Mobile layout is not required for v0.6.0 — this is a desktop operator tool.
- The wizard should be the best-looking single-purpose screen in the product. It is the first thing new users see.
