**Owner:** backend_developer, frontend_developer

---

## Problem

Iranti supports per-task model routing: operators can set different models for different task types using env vars:
- `CLASSIFICATION_MODEL`
- `RELEVANCE_MODEL`
- `SUMMARIZATION_MODEL`
- `TASK_INFERENCE_MODEL`
- `EXTRACTION_MODEL`
- `CONFLICT_MODEL`

This is a meaningful cost-optimization control — operators can use cheap models for fast tasks and expensive models for conflict resolution. The typical pattern: gemini-2.5-flash for everything except CONFLICT_MODEL which uses gemini-2.5-pro.

The Provider Manager currently shows the active provider and nothing about per-task routing.

---

## User Story

As an Iranti operator, I want to see and configure per-task model routing from the Provider Manager, so that I can optimize cost and quality without editing env files.

---

## Acceptance Criteria

1. Provider Manager shows a "Task Routing" section (below the default provider configuration).
2. For each task type (classification, relevance, summarization, task_inference, extraction, conflict), the section shows:
   - Current model (from env var, or "Using default" if not set)
   - Provider compatibility note (e.g. for `LLM_PROVIDER=gemini`, flash/pro models are valid)
3. Each task type has an "Override" dropdown populated with known models for the active provider.
4. "Clear Override" returns the task type to the default provider selection.
5. A "Reset All Overrides" action clears all 6 task-model env vars.
6. On save, the backend writes the updated task-model env vars to the instance env file.
7. The UI validates that the selected model is compatible with the active provider (e.g. cannot set `gemini-2.5-flash` when `LLM_PROVIDER=openai`) and shows a warning if incompatible.
8. Backend route:
   - `PUT /api/control-plane/providers/task-routing` — body: `{ overrides: Record<string, string | null> }` where null means "clear override"
9. `GET /api/control-plane/providers` response includes `taskRouting` field: `Record<string, string | null>`.

## Known model lists (for reference)

**OpenAI:** `gpt-5-mini`, `gpt-5`, `gpt-5-nano`, `gpt-3.5-turbo`
**Claude:** `claude-opus-4`, `claude-sonnet-4`, `claude-haiku-4`
**Groq:** `meta-llama/llama-4-scout-17b-16e-instruct`, `llama-3.1-70b-versatile`
**Mistral:** `mistral-small-latest`, `mistral-medium-latest`, `mistral-large-latest`
**Ollama:** user-defined model names (free text input)

## Implementation Notes

- Model list can be derived from the `providers.ts` backend which already has model listing logic.
- The incompatibility check (task model from wrong provider) should mirror Iranti's own behavior: log a warning, do not hard-block.
- If `LLM_PROVIDER` changes, task routing overrides may become incompatible — show a visual warning.
