# CP-T080 — Process Lifecycle Controls

**Type:** Feature (Backend + Frontend)
**Priority:** P1
**Assigned:** backend_developer + frontend_developer
**Phase:** 6 (Wave 15)
**Status:** OPEN
**Epic:** CP-E019 (Lifecycle Management)
**Depends on:** CP-T079 (install detection — must confirm iranti CLI is available before spawning it)

---

## Description

The control plane can see Iranti instances and their health, but cannot affect them. If an instance is unreachable, the operator must open a terminal and run `iranti run --instance <name>` manually. If they want to stop it, they must find and kill the process themselves.

This ticket adds Start and Stop buttons to the Instance Manager — the control plane equivalent of Docker Desktop's container start/stop controls. When a user sees an instance is unreachable, they can click Start. When it is running, they can click Stop. The control plane manages the subprocess lifecycle.

**Important scope note:** PID tracking for this ticket is in-memory only. If the control plane server process restarts, it loses track of spawned Iranti processes. This is acceptable for the v0.6.0 scope — the tradeoff is documented. A future ticket may add persistent PID tracking (e.g., writing PIDs to a `.iranti-pids.json` file).

## What to Build

### Backend — Start Endpoint

```
POST /api/control-plane/instances/:name/start
```

**Implementation:**

1. Validate instance name (alphanumeric, hyphens, underscores only — same as CP-T073 upgrade endpoint).
2. Check if iranti CLI is on PATH (same logic as CP-T079 install detection). If not found: return HTTP 400 with `"iranti CLI not found on PATH"`.
3. Check in-memory PID map — if this instance name already has a tracked PID and the process is still running: return HTTP 409 with `"Instance appears to already be running (PID: <n>)"`.
4. Spawn `iranti run --instance <name>` as a detached subprocess:
   - Use Node.js `child_process.spawn` with `detached: true` and `stdio: 'ignore'`
   - Call `childProcess.unref()` so the control plane process does not wait for it
5. Store the PID in an in-memory map: `{ [instanceName]: pid }`
6. Return HTTP 202 with:

```typescript
interface StartResponse {
  instanceName: string;
  pid: number;
  status: 'started';
  startedAt: string;
}
```

**Security:**
- Instance name must pass the same sanitization as CP-T073 (alphanumeric + hyphen + underscore, max 64 chars)
- Do not accept shell-interpretable characters — use `spawn` with an array of args, not `exec` with a shell string

**Audit log:** Write a start event to the control plane audit trail (same mechanism as CP-T033 repair actions).

### Backend — Stop Endpoint

```
POST /api/control-plane/instances/:name/stop
```

**Implementation:**

1. Validate instance name.
2. Look up the PID in the in-memory map.
3. If no PID tracked: attempt port-based kill as a fallback (see below). If no port is known either: return HTTP 404 with `"No tracked process for this instance. Stop it manually using your OS process manager."`.
4. If PID is tracked: send SIGTERM to the process. On Windows: use `process.kill(pid)` (sends SIGTERM on Unix, terminates on Windows).
5. Remove the PID from the in-memory map.
6. Return HTTP 200 with:

```typescript
interface StopResponse {
  instanceName: string;
  pid: number | null;
  status: 'stopped';
  stoppedAt: string;
}
```

**Port-based fallback (best-effort):**
- If the instance has a known port in its configuration, try to find and kill the process listening on that port using `fuser` (Linux), `lsof` (macOS), or `netstat`/`taskkill` (Windows).
- This is a stretch goal — if it adds significant complexity, document the limitation and return a clear error instead.

**Audit log:** Write a stop event to the audit trail.

**TypeScript:** Clean. No `any`. The in-memory PID map and both response interfaces must be typed.

### Frontend — Start / Stop Buttons in Instance Manager

**Where to add them:**

In the Instance Manager instance list, each instance card gets action buttons based on its reachability status:

- Instance **reachable (healthy or degraded):** Show a **Stop** button
- Instance **unreachable:** Show a **Start** button
- Instance **status unknown:** Show a **Start** button with a tooltip: "Status unknown — starting may create a duplicate process"

**Button placement:** Inside the instance card, aligned right (same row as the instance name and status badge). Do not bury them in the expanded detail panel — these are primary actions and must be visible without clicking.

**Start button flow:**

1. Operator clicks **Start** on an unreachable instance
2. Button shows a spinner and becomes disabled (preventing double-click)
3. Calls `POST /api/control-plane/instances/:name/start`
4. On success: show a brief "Starting..." status on the card
5. After 2 seconds, re-poll the instance health to check if it came online
6. If health check returns healthy: update the card status to healthy; Start button changes to Stop
7. If health check still fails after the re-poll: show "Started (connecting...)" — the instance process was spawned but may still be initialising

**Stop button flow:**

1. Operator clicks **Stop** on a running instance
2. Confirmation modal: "Stop `<instance-name>`?" — "This will terminate the Iranti process. Agents using this instance will lose connectivity." — Cancel / Stop
3. On confirm: calls `POST /api/control-plane/instances/:name/stop`
4. On success: update card status to unreachable; Stop button changes to Start
5. On error (e.g., process not tracked): show inline error message with the error detail

**Error states:**
- Start fails (iranti not on PATH): show "iranti CLI not found" inline error with a link to CP-T079 install guidance
- Stop fails (no tracked PID): show "Cannot stop — process not tracked by control plane. Stop manually." with a copy button for the kill command

## Acceptance Criteria

### AC-1 — Start button spawns `iranti run` correctly

`POST /api/control-plane/instances/:name/start` spawns `iranti run --instance <name>` as a detached subprocess and returns HTTP 202 with a PID. The process is not a child of the control plane (detached + unref'd — control plane can restart without killing the Iranti process).

### AC-2 — Stop button terminates the process

`POST /api/control-plane/instances/:name/stop` sends SIGTERM to the tracked PID and returns HTTP 200. The tracked PID is removed from the in-memory map.

### AC-3 — UI updates instance status after action

After Start: the instance card re-polls health after 2 seconds and reflects the new status (healthy or still connecting). After Stop: the instance card reflects unreachable status immediately. Button state (Start/Stop) reflects the current reachability.

### AC-4 — Graceful error if process fails to start

If `iranti run` exits immediately with a non-zero code (e.g., port already in use), the control plane detects this during the 2-second re-poll and shows an appropriate inline error rather than leaving the card in "Starting..." indefinitely.

### AC-5 — Instance name sanitized

Passing a path traversal or shell injection string as instance name returns HTTP 400 with "Invalid instance name." The subprocess is never spawned with an unsanitized name.

### AC-6 — PID tracking limitation documented

The in-memory PID tracking limitation (cleared on control plane restart) is documented in the Instance Manager UI with a brief note: "Process tracking is session-based — if the control plane restarts, use Start to reconnect to running instances."

### AC-7 — Audit log entries written

Start and Stop events are written to the control plane audit trail.

### AC-8 — tsc clean

`tsc --noEmit` passes with 0 errors in both `src/server` and `src/client`.

## Priority

P1 — core lifecycle management capability. Required by CP-T083 (Guided Setup Wizard step 3).

## Known Limitations (Acceptable for v0.6.0)

- PID tracking is in-memory. Restarting the control plane server clears the PID map. Operators can still start instances from the UI after a control plane restart — they just cannot stop previously-started instances via the UI.
- Port-based stop fallback is a stretch goal.
- No support for instances started outside the control plane (no orphan adoption).
