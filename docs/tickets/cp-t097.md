# CP-T097 — Bug: anthropic/claude Provider ID Drift

**Phase:** 7 (bug surfaced) / Fix target: v0.7.1 or v0.8.0
**Epic:** CP-E017
**Priority:** P1
**Status:** OPEN
**Owner:** backend_developer, frontend_developer
**Created:** 2026-03-22
**Surfaced by:** CP-T087 review

---

## Problem

The control plane writes `LLM_PROVIDER=anthropic` when the operator selects "Claude" as the default provider (CP-T085 / CP-T086). The Iranti LLM router expects `LLM_PROVIDER=claude`.

This is a pre-existing inconsistency between the control plane's provider ID convention and the upstream Iranti router's expected value. It was first explicitly documented during the CP-T087 (Task-Model Routing Editor) review.

**Impact:**
- Operators who use the control plane to set Claude as their default provider will see Iranti fall back to the fallback chain or error, because the router does not recognize `anthropic` as a valid provider ID.
- The Task Routing editor may also populate provider-specific model lists incorrectly (using `anthropic` key where `claude` is expected).
- The issue exists silently — Iranti does not loudly error on an unrecognized `LLM_PROVIDER` value in all code paths.

---

## Root Cause

The control plane's provider ID enum uses `anthropic` (the company name) while the Iranti router uses `claude` (the product name). Neither is wrong in isolation — the inconsistency is in the mapping between the two systems.

Relevant code locations:
- Provider ID enum in `src/server/routes/control-plane/providers.ts` — defines `anthropic` as the identifier for the Claude provider
- Iranti LLM router — uses `claude` as the canonical provider ID (as confirmed in cross-repo audit v0.2.16)

---

## Acceptance Criteria

1. The control plane uses `claude` as the canonical provider ID for all Claude API key operations, default provider writes, fallback chain entries, and task routing overrides.
2. `LLM_PROVIDER=claude` is written to the instance env when the operator selects Claude as the default provider.
3. `ANTHROPIC_API_KEY` continues to be used as the env var name for the Claude API key (this is correct and aligns with Iranti's key lookup).
4. Display label in the UI remains "Claude" (user-facing name is unchanged; only the internal env var value changes from `anthropic` → `claude`).
5. Any existing `LLM_PROVIDER=anthropic` value in operator env files is detected and flagged in the Provider Manager with a one-click fix ("Update to `claude`").
6. The known model list for Claude in the routing editor remains: `claude-opus-4`, `claude-sonnet-4`, `claude-haiku-4`.

---

## Implementation Notes

- The fix is primarily in `providers.ts`: change the provider ID constant for Claude from `'anthropic'` to `'claude'` in write operations.
- The `ANTHROPIC_API_KEY` env var name is NOT changed — this is the key variable, not the provider ID.
- Read operations: when reading `LLM_PROVIDER` from the env, treat both `anthropic` and `claude` as referring to the Claude provider (for backwards compatibility with existing env files). Write `claude` on any update.
- The migration hint in the Provider Manager (AC-5) can be implemented as a banner: "Your instance is configured with `LLM_PROVIDER=anthropic`. The Iranti router expects `claude`. [Fix now]" — shown only when the current value is `anthropic`.

---

## Workaround (until fixed)

Set `LLM_PROVIDER=claude` manually in the instance env file:
```
# C:\Users\NF\.iranti-runtime\instances\local\.env
LLM_PROVIDER=claude
```

Or edit via any text editor. The control plane's env merge strategy will preserve this value through other write operations as long as `LLM_PROVIDER` is not touched.
