# CP-T085 — Provider Key Write Path

**Phase:** 7 — Operator Configuration Management
**Epic:** CP-E017
**Priority:** P0
**Status:** OPEN
**Owner:** backend_developer, frontend_developer
**Created:** 2026-03-22

---

## Problem

The ProviderManager view is read-only. It shows which provider keys are present (masked) and whether the provider is reachable. But operators cannot add, rotate, or remove provider API keys from the UI. When a key expires or needs rotation, operators must use the terminal (`iranti add api-key <provider> --key sk-... --instance local`).

This breaks the core operator promise: "you should be able to manage Iranti configuration entirely from the control plane."

---

## User Story

As an Iranti operator, I want to add, update, and remove upstream provider API keys (OpenAI, Claude, Gemini, Groq, Mistral) from the Provider Manager in the control plane, so that I never need to drop to a terminal to rotate a key.

---

## Acceptance Criteria

1. The Provider Manager shows a "Manage Key" action for each configured provider (providers that support remote API keys only — not `mock`, `ollama`).
2. Clicking "Manage Key" opens an inline form or modal with:
   - masked current key display (last 4 chars)
   - "Update Key" input (masked text field)
   - "Remove Key" button with confirmation
3. The "Add Key" action is available for providers not yet configured.
4. On save, the backend writes the key to the instance env file (exactly as `iranti add api-key` does — same key variable names: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `GROQ_API_KEY`, `MISTRAL_API_KEY`).
5. The UI never exposes raw key values — write-only input with masked display only.
6. A "Set as Default Provider" toggle updates `LLM_PROVIDER` in the instance env.
7. After a key update, the provider reachability status refreshes automatically.
8. Error states are shown clearly: invalid key format, failed write, instance not found.
9. Backend routes:
   - `PUT /api/control-plane/providers/:provider/key` — set or update key (body: `{ key: string }`)
   - `DELETE /api/control-plane/providers/:provider/key` — remove key
   - `PUT /api/control-plane/providers/default` — set default provider (body: `{ provider: string }`)
10. Backend reads and writes instance env file using the same variable mapping as `iranti-cli.ts` add/update/remove provider key paths. Never exposes raw key values in API responses.

---

## Implementation Notes

- The backend must locate the active instance env file (same discovery path as other control plane routes: `process.env.IRANTI_INSTANCE_ENV` or the primary instance env).
- Env file writes must use the same merge strategy as the CLI: read existing, update target variable, write back. Do not truncate unrelated env vars.
- Placeholder values (`replace_me`, `sk-xxx`) must be rejected.
- For `--set-default` behavior: after writing the provider key, also update `LLM_PROVIDER` if the user checked the "Set as Default" option.
- Provider variable mapping (from `iranti-cli.ts` provider key spec):
  - `openai` → `OPENAI_API_KEY`
  - `claude` → `ANTHROPIC_API_KEY`
  - `gemini` → `GEMINI_API_KEY`
  - `groq` → `GROQ_API_KEY`
  - `mistral` → `MISTRAL_API_KEY`
