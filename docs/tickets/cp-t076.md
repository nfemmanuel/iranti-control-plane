**Type:** Frontend / Design System
**Priority:** P1
**Assigned:** frontend_developer
**Phase:** 6 (Wave 13)
**Status:** OPEN
**Epic:** CP-E017 (Brand Alignment)
**Depends on:** Nothing — design system change; all other Phase 6 tickets benefit from this landing first

---

## Description

The Iranti Control Plane currently uses a GitHub-dark blue-gray + emerald palette inherited from the original "Terminals" option chosen in Phase 0. The iranti-site (marketing site) ships a warm amber + teal + warm-ink palette that is distinctive and purpose-built for the Iranti brand.

These two products now look like they belong to different companies. Phase 6 corrects this by migrating `src/client/src/styles/tokens.css` to match the iranti-site palette exactly, while preserving the Staff component color identities (librarian, attendant, archivist, resolutionist) that users have already built mental models around.

This is a design system change, not a cosmetic one. All color decisions must flow from `tokens.css` design tokens — no hardcoded hex values anywhere in component CSS or inline styles.

## Target Palette

### Dark Mode (`:root` or `[data-theme="dark"]`)

**Backgrounds:**
- `--color-bg-base`: `#080808` — page/app background
- `--color-bg-surface`: `#111110` — card and panel surfaces
- `--color-bg-elevated`: `#1c1c1a` — modals, dropdowns, popovers
- `--color-bg-sunken`: `#050503` — inset wells, code blocks, input fills

**Borders:**
- `--color-border-subtle`: `#1c1c1a` — barely-there separators
- `--color-border-default`: `#2a2a28` — standard panel and card borders
- `--color-border-strong`: `#3d3d3a` — focused inputs, active selections

**Text:**
- `--color-text-primary`: `#f5f5f2` — all primary body text and headings
- `--color-text-secondary`: `#8a8a85` — labels, metadata, secondary descriptions
- `--color-text-tertiary`: `#5c5c58` — placeholders, muted hints, disabled text

**Accent — Amber (interactive / brand CTAs):**
- `--color-accent`: `#f59e0b` — primary buttons, active nav items, links
- `--color-accent-hover`: `#d97706` — hover state for accent elements
- `--color-accent-subtle`: `rgba(245, 158, 11, 0.12)` — accent background tints

**Success / Health — Teal (distinct from accent):**
- `--color-success`: `#14b8a6` — healthy indicators, check marks, passing checks
- `--color-success-hover`: `#0d9488` — hover state for success elements
- `--color-success-subtle`: `rgba(20, 184, 166, 0.12)` — success background tints

**Warning — Amber-Orange (shifted from accent to differentiate):**
- `--color-warning`: `#f97316` — warning badges, degraded states
- `--color-warning-hover`: `#ea580c` — hover state for warning elements
- `--color-warning-subtle`: `rgba(249, 115, 22, 0.12)` — warning background tints

**Error — Red (unchanged from existing):**
- `--color-error`: `#ef4444` — error states, critical failures
- `--color-error-hover`: `#dc2626`
- `--color-error-subtle`: `rgba(239, 68, 68, 0.12)`

**Informational — Existing blue (unchanged):**
- `--color-info`: `#3b82f6`
- `--color-info-subtle`: `rgba(59, 130, 246, 0.12)`

### Light Mode (`[data-theme="light"]`)

**Success — Teal:**
- `--color-success`: `#0f766e`

- `--color-warning-subtle`: `rgba(194, 65, 12, 0.08)`

### Staff Component Colors

Staff colors stay the same across both modes — they are identity colors, not semantic status colors. The one change is that Resolutionist's teal must now align with the new `--color-success` teal for visual consistency (they are now the same hue family):

| Staff Role | Color | Token |
|------------|-------|-------|
| Librarian | amber `#f59e0b` | `--color-staff-librarian` |
| Attendant | violet `#8b5cf6` | `--color-staff-attendant` |
| Archivist | sky `#0ea5e9` | `--color-staff-archivist` |
| Resolutionist | teal `#14b8a6` | `--color-staff-resolutionist` |

Note: Resolutionist and `--color-success` now share the same base hue. This is intentional — Resolutionist resolves conflicts (a "success" action), and the palette alignment is semantically correct.

### Typography

Add Inter as the primary sans-serif font, loaded via Google Fonts import or system font stack fallback:

```css
@import url('https://fonts.googleapis.com/css2?family=Inter:wght@400;500;600;700&display=swap');

--font-sans: 'Inter', -apple-system, BlinkMacSystemFont, 'Segoe UI', system-ui, sans-serif;
```

Monospace: keep existing (`--font-mono` unchanged — existing stack is appropriate).

## What to Build

### 1. Migrate `src/client/src/styles/tokens.css`

- Replace all existing color token values with the target palette above
- Add new semantic tokens not currently present (e.g., `--color-bg-sunken`, `--color-border-strong`, `--color-accent-subtle`)
- Add `--font-sans` token with Inter + system fallback
- Add Google Fonts `@import` at the top of the file (or the root CSS entry point if tokens.css does not accept imports)
- Ensure tokens are defined both in `:root`/`[data-theme="dark"]` and `[data-theme="light"]` blocks
- No hardcoded hex values should remain in `tokens.css` itself — all values must be defined once as tokens, then referenced by token name everywhere

### 2. Audit component CSS for hardcoded colors

Search `src/client/src/` for any hardcoded hex values (`#[0-9a-fA-F]{3,6}`), `rgb(`, and `rgba(` patterns that are not inside `tokens.css`. Replace each with the appropriate design token.

Common places to check:
- `AppShell.tsx` / `AppShell.css`
- `HealthDashboard.tsx` / `.css`
- `StaffActivity.tsx` / `.css`
- `InstanceManager.tsx` / `.css`
- Any chart or SVG drawing code in `MetricsDashboard.tsx` (chart colors should use tokens)

### 3. Verify Staff colors

After migration, open the Staff Activity Stream and confirm all four component types render with visually distinct colors. The four must not look the same in either light or dark mode.

### 4. TypeScript check

Run `tsc --noEmit` in `src/client` and confirm 0 errors. Color changes should be CSS-only and introduce no TypeScript errors, but verify because token renaming can break CSS Modules type references.

## Acceptance Criteria

### AC-1 — tokens.css fully migrated

`src/client/src/styles/tokens.css` defines the full new palette. No hardcoded hex values remain in `tokens.css` — all values are explicit token definitions. Old emerald/blue-gray tokens are removed or replaced.

### AC-2 — Dark mode renders correctly

In dark mode: background is warm near-black (`#080808` base), CTAs render in amber, healthy health indicators render in teal, warnings render in amber-orange (visually distinct from CTA amber), errors render in red. The overall impression matches the iranti-site dark palette.

### AC-3 — Light mode renders correctly

In light mode: background is warm sand off-white, text is near-black warm ink, amber CTAs remain legible at WCAG AA contrast ratio against sand backgrounds, teal health indicators remain legible. Toggling light/dark mode in the app produces a visually coherent switch.

### AC-4 — No tsc errors

`tsc --noEmit` passes with 0 errors in `src/client`. No regression from `src/server`.

### AC-5 — Staff component colors still visually distinct

The Staff Activity Stream shows four visually distinct component colors: amber (Librarian), violet (Attendant), sky (Archivist), and teal (Resolutionist). No two roles look the same in either light or dark mode. Resolutionist teal is harmonious with the new success teal.

### AC-6 — No hardcoded hex values in components

A search of `src/client/src/` (excluding `tokens.css`) returns no standalone hex color strings. All color usage references design tokens.

### AC-7 — Inter font loads

The control plane body text renders in Inter (or system-ui fallback if the font request fails). The font change is visible on load — the old font stack should be visibly different if Inter loads correctly.

## Notes for Implementer

- The existing Terminals palette (dark blue-gray / emerald) is intentionally removed. Do not preserve it as a fallback.
- The amber accent and amber-orange warning are intentionally close in hue — this is acceptable because the contexts in which they appear are distinct (CTAs vs. warning badges). If the implementer finds this confusing in practice, consult PM before changing the warning hue further.
- Resolutionist teal matching success teal is a deliberate product decision, not an oversight.
