# CP-T078 — Iranti Version Sync

**Type:** Feature (Backend + Frontend)
**Priority:** P2
**Assigned:** backend_developer (endpoint) + frontend_developer (UI)
**Phase:** 6 (Wave 14)
**Status:** OPEN
**Epic:** CP-E018 (Version Intelligence)
**Depends on:** CP-T076 (palette migration should be done first so version UI renders correctly)

---

## Description

Operators currently have no way to know whether the Iranti version they are running is the latest available. They must manually check `npm show iranti version` in a terminal and compare it to `iranti --version`. This is friction that belongs inside the control plane.

This ticket adds a version sync check: the control plane fetches the locally installed Iranti version from the running instance's `/health` endpoint and fetches the latest published version from the npm registry. It compares them and displays the result in the Health dashboard.

The result reads like: "Iranti v0.2.16 — Up to date" or "Update available: v0.2.17 → [Release notes]".

This also sets up the data dependency for CP-T081 (Upgrade From UI), which shows an "Upgrade Iranti" button when an update is available.

## What to Build

### Backend — Version Sync Endpoint

```
GET /api/control-plane/version-sync
```

**Implementation:**

1. Fetch installed version from Iranti's health endpoint:
   - Call `GET {instanceBaseUrl}/health`
   - Extract the `version` field from the response (Iranti `/health` returns a `version` string in its response body as of v0.2.16)
   - If `/health` is unreachable or `version` is absent: `installedVersion = null`

2. Fetch latest published version from npm registry:
   - Call `GET https://registry.npmjs.org/iranti/latest` with a 5-second timeout
   - Extract `version` field from the JSON response
   - If the registry is unreachable, times out, or returns non-200: `latestVersion = null`
   - Do NOT fail the entire endpoint if the registry is unreachable — return partial data with a `registryUnavailable: true` flag

3. Compare and return:

```typescript
interface VersionSyncResponse {
  installedVersion: string | null;  // from Iranti /health
  latestVersion: string | null;     // from npm registry
  upToDate: boolean;                // true if installedVersion === latestVersion
  releaseUrl: string;               // https://github.com/nfemmanuel/iranti/releases
  registryUnavailable: boolean;     // true if npm registry fetch failed
  checkedAt: string;                // ISO timestamp of when the check was performed
}
```

**Timeout behavior:**
- npm registry call: 5s timeout; on timeout set `latestVersion = null`, `registryUnavailable = true`
- Iranti `/health` call: use existing instance health timeout (same as health dashboard)
- Total endpoint latency should not exceed 6s (registry timeout + small overhead)

**Caching:**
- Cache the npm registry response for 60 seconds server-side (in-memory). The registry does not need to be hit on every page load.
- Do not cache the installed version — that should always reflect the live instance.

**Error handling:**
- If the active instance is not configured: return `{ installedVersion: null, latestVersion: <whatever>, upToDate: false, ... }`
- Never return 500 — always return 200 with null fields and flags set appropriately

**TypeScript:** Clean. No `any`. Add the `VersionSyncResponse` interface to the shared types.

### Frontend — Version Status Display

**Where to display:** In the Health Dashboard, as a dedicated version status row or compact card in the header area of the dashboard (above or alongside the existing health check cards).

**Layout:**

When up to date:
```
Iranti v0.2.16  ✓ Up to date
```

When update available:
```
Iranti v0.2.16  ↑ Update available: v0.2.17  [Release notes ↗]
```

When installed version unknown (Iranti unreachable):
```
Iranti version unknown  (connect to an instance to check)
```

When registry unavailable but installed version known:
```
Iranti v0.2.16  (unable to check for updates)
```

**Styling:**
- "Up to date" indicator uses `--color-success` (teal) — matches health check pass styling
- "Update available" indicator uses `--color-warning` (amber-orange) — matches health check degraded styling
- "Release notes" link opens in a new tab
- The component should be small — this is status information, not a primary action surface

**Data fetching:**
- Call `GET /api/control-plane/version-sync` on Health Dashboard mount
- Refresh on the same interval as health checks (or on explicit user refresh)
- Show a skeleton/placeholder while loading; never show stale "up to date" from a previous session

## Acceptance Criteria

### AC-1 — Endpoint returns correct installed version

`GET /api/control-plane/version-sync` returns the Iranti version string from the running instance's `/health` response in the `installedVersion` field.

### AC-2 — Endpoint fetches latest from npm registry with timeout and fallback

If the npm registry responds: `latestVersion` is populated. If the registry times out (after 5s) or returns an error: `latestVersion = null`, `registryUnavailable = true`. The endpoint still returns 200 in either case.

### AC-3 — UI shows version sync status on Health Dashboard

The Health Dashboard includes a version status display showing the installed version and update state. It is visible without scrolling on a standard 1080p display.

### AC-4 — "Update available" state links to GitHub releases

When `upToDate === false` and `latestVersion !== null`, the UI shows "Update available: vX.Y.Z" with a "Release notes" link pointing to `https://github.com/nfemmanuel/iranti/releases`.

### AC-5 — No errors if either source unavailable

If Iranti is unreachable: installed version shows as unknown, UI renders a graceful "connect to an instance" message. If npm registry is unavailable: UI shows "unable to check for updates" alongside the installed version. Neither condition causes a crash or unhandled rejection.

### AC-6 — tsc clean

`tsc --noEmit` passes with 0 errors in both `src/server` and `src/client` after this ticket.
