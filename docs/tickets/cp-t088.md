# CP-T088 — Iranti Client API Key Manager

**Phase:** 7 — Operator Configuration Management
**Epic:** CP-E017
**Priority:** P0
**Status:** OPEN
**Owner:** backend_developer, frontend_developer
**Created:** 2026-03-22

---

## Problem

Iranti uses registry-backed API keys to authorize apps and agents (`iranti auth create-key`, `iranti auth list-keys`, `iranti auth revoke-key`). These keys are distinct from upstream provider API keys (OpenAI, Claude, etc.) — they are the tokens that agents, Claude Code integrations, and project bindings use to authenticate against the Iranti instance.

The control plane has **no surface** for this. CP-T063 (API Key Scope Audit) added a view that reads scopes from the project `.env.iranti`, but:
- It does not list all keys registered in the instance database
- It cannot create new keys
- It cannot revoke existing keys
- It cannot show which key belongs to which owner/agent

This is a critical operational gap. When a project needs a new API key, or a key is compromised, operators must use standalone scripts or the CLI. There is no way to do this from the control plane.

---

## User Story

As an Iranti operator, I want to see all registered API keys for my instance, create new keys with specific scopes, and revoke compromised or stale keys — all from the control plane.

---

## Acceptance Criteria

1. A new "API Keys" section exists within the Instance Manager (or as a sub-panel of the instance detail view).
2. The section lists all registry-backed API keys for the selected instance with:
   - Key ID
   - Owner label
   - Scopes (displayed as readable tags: `kb:read`, `memory:write`, etc.)
   - Creation timestamp
   - Last modified timestamp
   - Active / Revoked status
3. "Create Key" action opens a form:
   - Key ID (stable identifier, required)
   - Owner label (required)
   - Scope selector (checkboxes for standard scopes: `kb:read`, `kb:write`, `memory:read`, `memory:write`, `agents:read`, `agents:write`, `metrics:read`)
   - Namespace-aware scope input (free text, optional: `kb:read:project/acme`)
   - "Copy to project" option (select a bound project to sync the token into its `.env.iranti`)
4. After "Create Key", the generated token is shown **once** in a copy-only field with a clear warning that it will not be shown again.
5. "Revoke Key" action marks the key inactive with a confirmation dialog showing the key ID and owner.
6. Revoked keys remain visible in the list with their revoked status (for audit).
7. The section shows an empty state when no keys are registered: "No API keys registered. Run iranti setup or create your first key here."
8. Backend routes:
   - `GET /api/control-plane/auth-keys` — list all keys for the active instance (never return raw token values)
   - `POST /api/control-plane/auth-keys` — create/rotate a key (body: `{ keyId, owner, scopes, description?, syncToProject? }`)
   - `DELETE /api/control-plane/auth-keys/:keyId` — revoke a key
9. The backend connects to the instance DB using the same `DATABASE_URL` as the running Iranti instance, using the same registry operations as `iranti auth create-key`.
10. The backend never returns raw token values — only the masked form (`keyId.****`) for display.

---

## Implementation Notes

- The backend for this ticket connects to the Iranti instance database directly — it needs access to the `api_keys` table (or equivalent). Reference `scripts/api-key-create.ts`, `api-key-list.ts`, `api-key-revoke.ts` for the existing registry API.
- Token generation: on creation, the backend returns the full `keyId.secret` token exactly once. Store only the hashed form in the DB as the existing registry does.
- For the "sync to project" flow: after key creation, write the token into the selected project's `.env.iranti` as `IRANTI_API_KEY`.
- Scope validation: use the same namespace-aware scope parser as `src/security/scopes.ts`.
