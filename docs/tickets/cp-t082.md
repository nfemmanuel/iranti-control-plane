---

## Description

The Health Dashboard currently shows a list of health checks (iranti connectivity, auth, DB, vector backend, ingest round-trip, Attendant status, vector search) with pass/fail status. When a check fails, the operator sees a red indicator and a message — but no next step. They must figure out on their own what to do about it.

CP-T033 (Phase 2) added repair buttons for specific integration repair actions (fix MCP JSON, update CLAUDE.md, run doctor). Those are good but they are general-purpose repairs, not specific to the health check that failed.

This ticket adds **contextual repair actions** to each health check card: when a check fails, the card shows a specific, relevant action button or link that takes the operator directly to the right place to resolve it.

These actions are additive to the existing CP-T033 repair buttons — they appear on the health check cards themselves, not in the repair panel.

## Check-to-Action Map

| Check ID | Failing Action | Action Type |
|----------|---------------|-------------|
| `iranti_connectivity` | **Start Iranti** button | Triggers CP-T080 start for the active instance |
| `iranti_auth` | **Configure API Key** button/link | Navigate to `/providers` (Provider Manager view) |
| `db_connectivity` | **Check DB config** — shows connection string hint + link to getting-started#database | Inline info panel |
| `vector_backend` | **View setup guide** link | Opens `/getting-started#vector-backend` or the relevant guide section |
| `ingest_roundtrip` | **Run diagnostics** button | Triggers the CP-T059 diagnostics panel (opens/scrolls to it) |
| `attend_check` | **View Attendant logs** link | Navigates to `/logs` with the Attendant component filter pre-applied |
| `vector_search_check` | **Check vector backend** button/link | Same action as `vector_backend` above — link to setup guide |

### Action Specifications

**`iranti_connectivity` → Start Iranti:**

The most important action. When Iranti connectivity fails, operators often need to start the instance. Clicking "Start Iranti" should:
1. Trigger `POST /api/control-plane/instances/:name/start` (CP-T080 endpoint)
2. Show a spinner on the button while the start call is in-flight
3. After 2 seconds, re-poll health to update the `iranti_connectivity` check status
4. If the check passes: button disappears, card shows healthy
5. If the check still fails: show "Started — still connecting..." with a re-poll countdown

This button only appears if CP-T080 is implemented. If CP-T080 is not yet merged when this ticket is implemented: show "Connect to a running Iranti instance" as a static hint instead.

**`iranti_auth` → Configure API Key:**

A simple navigation link rendered as a button. Opens the Provider Manager at `/providers`. No new API call required.

**`db_connectivity` → Check DB config:**

When the DB check fails, show a small inline info section beneath the check card:
- The configured `DATABASE_URL` (redacted — show `postgres://***:***@host:port/dbname` — mask credentials, show host/port/name only)
- A link: "Getting started guide: Database configuration"
- A copy button for the full connection string (unredacted — behind a "Show" toggle)

This requires reading the DB config from the server (the `DATABASE_URL` env var, redacted). A new endpoint or an extension to the existing health endpoint may be needed. If the health endpoint already includes the DB host in its response, use that. If not, backend_developer should expose a `dbConfigHint` field in the health response (host and port only — never credentials in the response).

**`vector_backend` → View setup guide:**

A link that navigates to the Getting Started view (`/getting-started`) scrolled to the vector backend section, or directly to the relevant docs URL if one exists. This is a simple anchor link — no new API needed.

**`ingest_roundtrip` → Run diagnostics:**

When the ingest round-trip check fails, operators should run the interactive diagnostics panel (CP-T059). The button should:
1. Navigate to the Health Dashboard scroll position where the diagnostics panel lives (if on the same page), OR
2. Open the diagnostics panel (if it is a modal/expandable panel), OR
3. Navigate to `/health#diagnostics` if the panel is a dedicated section

Implement whichever of these is cleanest given the current diagnostics panel implementation.

**`attend_check` → View Attendant logs:**

Navigate to `/logs` with `?component=attendant` (or equivalent filter query param) pre-applied, so the logs view opens directly showing Attendant events. If the logs view does not support URL-driven filter state, add support for `?component=` query param as a minor enhancement to the Logs view.

**`vector_search_check` → Check vector backend:**

Same action as `vector_backend` — link to setup guide. These two checks often fail for the same underlying reason (vector backend not configured), so the action is the same.

## What to Build

### Frontend — Contextual Action Buttons on Health Check Cards

**When to show:** Only when the check status is `failing` or `degraded`. No action button shown when check is `passing` or `informational`.

**UI placement:** Beneath the check status message, inside the check card. Small button, secondary style (not the primary amber CTA — these are utility actions, not primary brand actions).

**Button labels and styles:**
- "Start Iranti" — primary-ish, since this is the most urgent possible action (instance is down)
- "Configure API Key" — secondary link-style
- "Check DB config" — secondary, expands inline panel
- "View setup guide" — text link with external link icon
- "Run diagnostics" — secondary button
- "View Attendant logs" — text link
- "Check vector backend" — text link with external link icon

### Backend (if needed)

**DB config hint:** If the existing health endpoint does not expose the database host and port in its response, add a `dbConfigHint: { host: string, port: number, database: string }` field to the health response. Credentials must NOT be included — host, port, and database name only.

**`?component=` filter for Logs view:** If the Staff Logs view (CP-T050) does not already support URL-driven filter state, add `?component=attendant` (and other values) to the route such that navigating to `/logs?component=attendant` pre-applies the component filter. This is a minor Logs view enhancement, likely 10-20 lines.

## Acceptance Criteria

### AC-1 — Each failing check shows a relevant action button

All seven health check IDs in the map above show their corresponding action button or link when the check is in a failing or degraded state.

### AC-2 — Actions navigate or trigger correctly

- "Start Iranti" calls the CP-T080 start endpoint and re-polls health
- "Configure API Key" navigates to `/providers`
- "Check DB config" expands an inline info panel with DB host/port/database (credentials masked)
- "View setup guide" navigates to the getting-started guide (or relevant section)
- "Run diagnostics" opens or focuses the CP-T059 diagnostics panel
- "View Attendant logs" navigates to `/logs?component=attendant`
- "Check vector backend" navigates to the vector backend setup guide

### AC-3 — No action shown when check passes

When a health check is in `passing` state, no action button is rendered. The card is clean.

### AC-4 — DB config masked correctly

When the "Check DB config" inline panel is shown, the database URL displayed masks credentials. The host, port, and database name are visible. A "Show full connection string" toggle (behind a click) can reveal the full unmasked string. Never show credentials in the default view.

### AC-5 — tsc clean

`tsc --noEmit` passes with 0 errors in both `src/server` and `src/client`.
