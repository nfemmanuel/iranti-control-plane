# CP-T092 — Claude Code Integration Manager

**Phase:** 7 — Operator Configuration Management
**Epic:** CP-E017
**Priority:** P1
**Status:** PM-ACCEPTED 2026-03-22
**Owner:** backend_developer, frontend_developer
**Created:** 2026-03-22

---

## Problem

The control plane shows whether Claude Code integration files exist for a project (MCP configured: ✓/✗, hooks configured: ✓/✗) but cannot:
- Show the actual content of `.mcp.json` (which MCP servers are registered, what args they use)
- Show the actual hook commands in `.claude/settings.local.json`
- Run `iranti claude-setup .` to scaffold or repair integration files
- Help diagnose why a hook is failing (wrong path, missing env var, stale command)

When Claude Code can't find Iranti tools, or hooks aren't firing, operators have no diagnostic starting point in the control plane. They must open these files manually and compare against the expected format.

---

## User Story

As an Iranti operator, I want to see the full Claude Code integration state for each project and scaffold or repair the integration files from the control plane, so that I can diagnose and fix Claude Code integration issues without opening files manually.

---

## Acceptance Criteria

**Visibility:**
1. Each project binding in the Instance Manager has a "Claude Integration" expandable section showing:
   - `.mcp.json` status: present/absent, content summary (list of registered MCP servers, specifically whether `iranti` is registered and what args it uses)
   - `.claude/settings.local.json` status: present/absent, hooks summary (list of configured hook events and commands)
   - Whether `IRANTI_URL` in the linked `.env.iranti` matches what `.mcp.json` / hooks would derive
2. If the integration files are missing or stale (e.g. wrong `iranti` command path), show a clear diagnostic message explaining the likely failure mode.
3. Raw file preview: clicking "View .mcp.json" or "View settings.local.json" opens a read-only code viewer with the file content.

**Scaffolding:**
4. "Scaffold Claude Integration" button: calls the equivalent of `iranti claude-setup .` for the project directory, writing or updating `.mcp.json` and `.claude/settings.local.json`.
5. If files already exist, the action shows a confirmation: "This will update existing integration files. Existing MCP servers other than Iranti will be preserved."
6. After scaffolding, the integration summary refreshes to show the updated state.
7. A "Re-scaffold (force)" option (for overwriting stale files with a fresh generation).

**Backend routes:**
8. `GET /api/control-plane/instances/:name/projects/:projectId/claude-integration` — returns: `{ mcpJson: object | null, hooksJson: object | null, irantiMcpEntry: object | null, irantiHooks: object | null, issues: string[] }`
9. `POST /api/control-plane/instances/:name/projects/:projectId/claude-integration/scaffold` — runs scaffold (force flag in body)

---

## Implementation Notes

- `.mcp.json` parsing: find the `iranti` key under `mcpServers`. If `command` is `iranti` and `args` contains `mcp`, integration is correctly configured.
- `.claude/settings.local.json` parsing: look for `SessionStart` and `UserPromptSubmit` hooks with `iranti claude-hook` commands.
- "Issues" array examples:
  - "`.mcp.json` not found — Claude Code cannot discover Iranti tools"
  - "Iranti MCP server not registered in `.mcp.json`"
  - "`iranti` command not found on PATH — hook will fail"
  - "Hook command uses absolute path — may fail after Iranti reinstall"
- The scaffold backend can call `iranti claude-setup <projectPath>` as a subprocess. This is the safest path to ensure parity with CLI behavior.
