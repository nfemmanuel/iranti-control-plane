# CP-T091 — Project Binding Create + Rebind

**Phase:** 7 — Operator Configuration Management
**Epic:** CP-E017
**Priority:** P1
**Status:** OPEN
**Owner:** backend_developer, frontend_developer
**Created:** 2026-03-22

---

## Problem

The Instance Manager shows project bindings read-only. Operators cannot:
- Bind a new project to an instance from the UI
- Rebind an existing project to a different instance
- Change a project's mode (isolated → shared or vice versa)

This requires `iranti project init .` or `iranti configure project . --interactive`. These are common onboarding and migration operations that operators should be able to do from the control plane.

This gap was partially acknowledged as CP-T033 (Integration Repair Actions) but CP-T033 focused on repair buttons for existing projects, not the create/rebind flows.

---

## User Story

As an Iranti operator, I want to bind a new project to an instance and rebind an existing project to a different instance from the Instance Manager, so that I can manage project-instance relationships without the terminal.

---

## Acceptance Criteria

**Project Binding Create:**
1. Each instance in the Instance Manager has a "Bind Project" button.
2. Clicking it opens a project binding form:
   - Project directory path (text input or directory picker if browser allows)
   - Mode selector: `isolated` (default) or `shared`
   - Agent ID (default: `main_agent` or based on project directory name)
   - Memory entity (default: `project/<dir_name>`)
3. On submit, the backend writes `.env.iranti` into the selected project directory with `IRANTI_URL`, `IRANTI_API_KEY`, `IRANTI_AGENT_ID`, `IRANTI_MEMORY_ENTITY`, `IRANTI_PROJECT_MODE`, `IRANTI_INSTANCE`, `IRANTI_INSTANCE_ENV`.
4. The project binding appears in the instance's project list after creation.
5. Optionally adds `.env.iranti` to the project's `.gitignore` (same as CLI behavior).

**Project Rebind:**
6. Each existing project binding has a "Rebind" action.
7. Clicking it opens a rebind form: new instance selector (dropdown of known instances).
8. On submit, the backend updates `IRANTI_URL`, `IRANTI_API_KEY`, `IRANTI_INSTANCE`, `IRANTI_INSTANCE_ENV` in the existing `.env.iranti` while preserving `IRANTI_AGENT_ID`, `IRANTI_MEMORY_ENTITY`, `IRANTI_PROJECT_MODE`.
9. After rebind, the project appears under the new instance in the Instance Manager.

**Backend routes:**
10. `POST /api/control-plane/instances/:name/projects` — bind a new project (body: `{ projectPath, mode, agentId?, memoryEntity? }`)
11. `PATCH /api/control-plane/instances/:name/projects/:projectId` — rebind or update (body: `{ instanceName?, mode? }`)

---

## Implementation Notes

- For the "directory picker": on Windows and macOS, the browser `<input type="file" webkitdirectory>` can select a folder. Alternatively, a text input for the path is acceptable for v1.
- The backend must validate that the project path exists and is a directory before writing.
- API key for the project binding: use the instance's `IRANTI_API_KEY` from its env file.
- Mode validation: `isolated` is the default. `shared` is only valid when explicitly chosen.
- A newly bound project does not automatically get Claude Code scaffolding — that is CP-T092.
