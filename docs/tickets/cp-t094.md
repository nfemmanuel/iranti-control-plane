# CP-T094 — Session Recovery Actions — Verify and Wire Resume/Abandon

**Phase:** 7 — Operator Configuration Management
**Epic:** CP-E017
**Priority:** P1
**Status:** OPEN
**Owner:** backend_developer, frontend_developer, qa_engineer
**Created:** 2026-03-22

---

## Problem

The SessionsView (CP-T071) shows interrupted agent sessions — session ID, agent ID, task summary, interrupted timestamp, last checkpoint payload. But it is unclear whether the UI actually exposes write actions (resume, abandon) or is read-only.

The Iranti SDK supports `resumeSession()` and `abandonSession()` programmatically. The control plane should expose these as operator actions — letting an operator look at an interrupted session and decide to formally abandon it, rather than having it linger indefinitely as an unresolved interrupted state.

---

## User Story

As an Iranti operator, I want to view interrupted sessions and take action on them (resume or abandon) from the Sessions view, so that I can keep session state clean without using the SDK directly.

---

## Investigation Task (first)

Before implementation, a developer must:
1. Read `SessionsView.tsx` and the `sessions.ts` backend route.
2. Determine: does the Sessions view currently support abandon/resume write actions, or is it read-only?
3. Check: does `sessions.ts` have `POST /sessions/:id/resume` and `POST /sessions/:id/abandon` routes?

If write actions already exist and are wired correctly: **close this ticket with a QA acceptance note.**
If they are missing or incomplete: proceed with implementation below.

---

## Acceptance Criteria

1. Sessions view shows each interrupted session with at minimum:
   - Agent ID
   - Session ID
   - Task summary (last known)
   - Interrupted at timestamp
   - Checkpoint preview (last step, next step, if available)
2. Each session has an "Abandon" button with confirmation: "Mark this session as abandoned. The checkpoint is preserved for audit but the session will no longer appear as interrupted."
3. Each session that has a checkpoint with a next step shows a "Resume note" indicator — not an automated resume button (resuming requires an agent; the CP can only surface the state and mark it ready for resume).
4. "Abandon" action calls `POST /api/control-plane/sessions/:sessionId/abandon`.
5. After abandon, the session moves from "interrupted" to "abandoned" status in the list (or is removed from the active view depending on filter state).
6. Empty state: "No interrupted sessions." when all sessions are resolved.
7. Backend route (if missing): `POST /api/control-plane/sessions/:sessionId/abandon` — marks session record status as `abandoned` in the Iranti KB.

---

## Implementation Notes

- The abandon operation writes to Iranti's knowledge base (updates the session record's status field). Use the Iranti HTTP API's write endpoint: `POST /kb/write` with the session record key, updating `task_status` to `abandoned`.
- Resume is a SDK-side operation — the control plane cannot "restart" an agent. The resume action should display the checkpoint payload in a readable way and offer a "Copy checkpoint to clipboard" action, so an operator or agent can use it when starting a new session.
- The sessions backend already reads from Iranti's KB. The abandon write should go through the same path.
